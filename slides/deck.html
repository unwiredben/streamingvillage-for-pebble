Pebble watchface · four platforms · built by Claude

Streaming Village

A parallax cityscape at sunset, on a 64‑colour watch display with 64KB of heap to spend. This is how it got built — and which parts of the work sit outside what a software engineer is usually asked to do.

Above: the watchface's dithered sunset, redrawn live by the same method tools/gen_art.py uses — nine colour stops, van der Corput thresholds.

02 · Beyond the ask

Two files that cannot drift apart

The artwork generator and the watchface both need the scene's geometry. Writing it down twice is the obvious approach, and it guarantees the two will disagree eventually.

Instead every length is derived from the 200×228 emery reference by the same integer scaling in both files. Both scalings are the identity at that size, so the emery numbers fall out of the macros unchanged.

The relationships the layout rests on — the ridge sitting on the sky's bottom edge, the street landing on the bottom of the display, a billboard tile being one display plus one board — are asserted in tests. Drift fails a check instead of showing up as a seam on someone's wrist.

src/c/main.c

#define SCALE_X(v) ((v) * PBL_DISPLAY_WIDTH / EMERY_W) #define SCALE_Y(v) ((v) * PBL_DISPLAY_HEIGHT / EMERY_H) #define SKY_H SCALE_Y(88) #define BG_H SCALE_Y(40) #define BB_TILE_W (PBL_DISPLAY_WIDTH + BB_FRAME_W)

Nothing in city_layer.c knows a display size at all. Only three values genuinely differ per platform: the billboard's panel margin, the clock font, and gabbro's tile count.

03 · The real constraint

The heap decided what the art could be

emery58.7 / 128 KB
basalt30.9 / 64 KB
chalk41.5 / 64 KB
gabbro86.9 / 128 KB

Resident bitmap tiles against the app heap. chalk is the tightest of the four: basalt's 64KB heap, a display half again as large in area, about 13KB clear once the tiles are in.

Two tiles resident per scrolling layer, each palettised at the narrowest bit depth its colour count allows — which is why the mountains cost two bits a pixel and the skyline four.

Resources ship as pbi, not png. PNG would be far smaller on flash, and decoding one needs a transient buffer on top of everything already resident, while tiles load mid‑animation.

04 · Beyond the ask

A distribution limit, folded back into the artwork

237KB8 tiles alone
256KBstore ceiling
6tiles shipped

gabbro's foreground panorama is six tiles rather than eight. Eight 260×228 tiles are 29,640 bytes each — 237KB of a 256KB resource budget before the sky, the ridge or the billboard get a byte, and a pack around 283KB.

That builds and sideloads fine: the hard limit is 1024KB. It is the appstore's ceiling it fails, which is a constraint that only shows up when you think about the watchface actually being published.

Six tiles is a 1560px loop, about 104 seconds of scrolling, and nothing on the watch notices — city_layer reads its tile count from the array it is handed. Two bitmaps are kept out of gabbro's pack entirely, and a test sizes every platform's pack against the budget.

05 · Beyond the ask

The textbook answer, tried and rejected

A 64‑colour display cannot render a sunset, so the gradient has to be dithered. The standard tool is a Bayer matrix. On this particular gradient it fails visibly — so the watchface uses something else.

Bayer 8×8 — the default Each row of the matrix spans only part of the threshold range, so in a purely vertical fade neighbouring rows land at different densities: horizontal streaks.
van der Corput — what shipped Every row walks the full 0–63 range in bit‑reversed order, so any prefix is spread evenly, and each row is rotated by its own random amount so the dots never line up into columns or diagonals.

Both panels are drawn here from the same nine stops the watchface uses, one 85‑per‑channel step apart — the smallest step a 64‑colour display can make.

06 · Beyond the ask

Someone has to wear this all day

A watchface that scrolls continuously is a watchface that flattens a battery. This one animates in bursts: two billboard passes when the face is activated or the watch is tapped, then it holds still with the billboard centred and the time on it.

Within a run, the three layers move in fractions of a pixel, so a redraw is only requested when an integer pixel position actually changes — and nothing is redrawn at all during the billboard's two‑second stall.

Both figures are pinned by tests/power_savings.c: change the geometry and the test tells you the new count rather than quietly letting the cost drift.

386timer steps
366redraws asked for

The subtlety underneath

Activation fires .appear and did_focus about a second apart, so starting a run has to be idempotent: it sets the pass count rather than adding to it, and a run already going keeps its existing timer. A tap resets the count instead of extending the run. A tap while unfocused cannot start one at all.

07 · Beyond the ask

Three harnesses nobody asked for

A watchface is awkward to test: the code only runs on a watch, and the output is pixels. So the parts that could be pulled onto the host, were.

Execute the macros, don't re-derive them

The layout #define block was lifted into its own header and compiled per platform by a nine‑line C program that prints what the arithmetic actually produces — real preprocessor, real integer division, no hand‑checked multiplication.

Composite the scene without a watch

A host script imports the generator, decodes the produced PNGs with zlib and struct by hand — no image library available — and stacks the layers in main.c's draw order to preview the scene at rest.

Checksum the artwork

Because the per‑platform scaling is the identity at 200×228, regenerating must leave the emery PNGs byte‑identical. Recorded hashes make that the regression test for any change to the generator.

Compile the watchface for the host

The host checks include main.c itself with timers and graphics replaced by recording stubs, then cover focus loss, taps, redraw counts, minute updates, notification offsets, and billboard placement at every scroll position in a tile.

Part two

“Capture an animation for the storefronts”

One sentence of a request. The four files it produced took the rest of the session, because almost nothing about the obvious approach survived contact with the problem.

What follows is the part of engineering that does not appear in a ticket: rejecting the tool that looks right, reading the source for numbers nobody wrote down, being wrong in a way that gets caught, and checking the output at the level the format is actually defined at.

08 · Beyond the ask

The built-in tool was the wrong tool

What it does

pebble screenshot --gif-all-platforms exists precisely for this job. It waits for the next wall‑clock minute boundary — between 8 and 68 seconds — then records a fixed seven‑second clip, so the minute digit rolls over on camera.

Why it cannot work here

This watchface animates in bursts and then stops. By the time that capture begins, the run triggered by installing the app is long over. The clip would be a still skyline with a ticking clock — technically a successful capture of the wrong thing.

Reading its implementation first was the cheap part. Its emulator plumbing, install sequence, frame grabbing and brightness handling were all worth reusing; only its capture window had to go.

A tool that runs without error, and produces a file, and is still wrong, is the failure mode worth looking for before pressing go.

09 · Beyond the ask

Proving what the loop could be, before capturing it

How long is one pass? Not measured — derived, from the constants in main.c: a 230px tile at 1.5px per frame, plus a 2000ms stall at 50ms per frame, is 193 frames on basalt.

Then the harder question: can the loop be seamless? The three layers repeat every 193, 1536 and 4608 frames. Those periods are incommensurate, so no clip shorter than minutes returns the whole scene to its starting state. That is a property of the design, and it settles the question before a single frame is recorded.

So the cut goes where it costs least: one billboard pass, which puts the billboard, the clock and the road in exactly the same place on both sides, and lets only the skyline behind them step along.

10 · Beyond the ask

Measure the thing, not something correlated with it

Finding the end of a pass by comparing whole frames does not work: the two layers that cannot line up dominate any image difference. That method picked a frame most of a pass away, with the billboard at the opposite edge.

So the script measures the one thing that defines a pass — the clock panel's horizontal centre. The panel is the only near‑white object in its band, so thresholding on the smallest channel finds it and ignores the coloured windows around it.

Real data from the delivered basalt loop. The pass ends where the trace comes back to the dashed line.

11 · Beyond the ask

Three wrong answers, each caught by its own check

8.75s Whole‑frame image difference picked the seam. Caught by looking at the chosen frame: the billboard was at the right edge, not centred. Replaced with the panel‑centre measurement.
22.90s vs 15.85s The search took the best match anywhere in the capture. If the scene comes to rest inside the window — which it can, because a run ends after a number of billboard crossings, not a number of seconds — every resting frame ties with the first one and a late frame wins by luck. Now the emulator is watched until the scene stops before the capture starts.
5.85s, +48.5px Walking outward until the distance grew. Stray near‑white pixels from lit windows jitter the measured centre by a fraction of a pixel, so the walk stopped on the jitter. Now the search is confined to the single crossing between one stall and the next.

None of these three produced an error. Each produced a plausible file that was wrong, which is why each is now a hard failure rather than a bad output.

12 · Beyond the ask

The format did not support the answer

A GIF holds no frame rate. It holds a delay per frame, in whole hundredths of a second. None of these passes runs at a rate that divides into that: basalt's 18.4fps rounds to 5cs and plays 8% fast — discarding the timing work that made the animation match real hardware in the first place.

Rounding each frame's cumulative position instead spreads the error. Frames come out 5cs or 6cs — a 10ms difference nobody can see — and the total is exact.

ffmpeg can only be told a constant rate, and feeding it per‑frame durations through the concat demuxer came back quantised into a 4cs/8cs stutter. So the delays are written into the encoded file afterwards: two bytes inside each frame's control block. ffmpeg is still worth keeping for the encode — it rewrites unchanged pixels as the transparent index, which halves the file against writing whole frames.

basalt 9.650s want 9.65 chalk 11.550s want 11.55 emery 12.650s want 12.65 gabbro 15.850s want 15.85 delays: {5: 97, 6: 80} — summed from the file's own control blocks

And the number that explained itself

Checking the GIFs against the lossless masters, the two round watches showed 20.7% and 21.5% of pixels differing. Alarming — until the figure is recognised: 1 − π/4 = 21.46%, the fraction of a square outside its inscribed circle. It was the hidden colour underneath the transparent corners. Nothing visible was affected.

13 · Where the line actually is

Things outside the request, and things still wrong

Volunteered

  • Noticed that a commit had renamed two screenshots and left the readme pointing at files that no longer existed — reported and fixed.
  • Found that ffmpeg's brightness filter truncates: it produced 169 where the display's colour grid has 170.
  • Declined to “fix” that by snapping every colour to the grid, because it would also flatten the antialiased rim on the round displays. Flagged it as a decision rather than making it quietly.

Still true, and worth saying

  • I have no memory of the earlier sessions. Everything in part one was reconstructed from the code, the readme, a device log and a scratch directory — not recalled.
  • The colour reconstruction is still one level off in places; the emulator floors some channels when it dims the panel, and no single scale recovers them.
  • The emulator is not a watch. Its timers run a few percent off, and under load gabbro stretched 19.0s against a 15.85s pass.
  • gabbro's GIF is 2.2MB. It fits, but it is the one I would watch on upload.

The store, for the record, rejects WebP outright and accepts an APNG upload while serving back only its first frame. Which is how the deliverable ended up being a GIF.
